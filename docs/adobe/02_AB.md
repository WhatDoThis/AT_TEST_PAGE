# Adobe Target A/B 테스트 가이드

> **A/B Test = 두 개 이상의 콘텐츠 변형을 비교해 "어느 것이 더 잘 전환되는지" 데이터로 찾는 활동.**
> **목적:** A/B 개념·트래픽 분배·통계·세팅을 한눈에. 실제 코드 연동은 `docs/main/04_AT_TEST_PAGE_ADOBE_TARGET_INTEGRATION.md`.

**한 줄 핵심**

```text
변형 A·B…N 만들기 → 트래픽 랜덤 분배(예: 50/50) → 목표 지표로 성과 측정 → 승자 판정
```

> XT와의 차이: **A/B = "무엇이 이기는지 발견"(랜덤·통계), XT = "정해진 답을 대상별 전달"(오디언스 규칙).** 자세히 `01_XT.md §2`.

---

## 0. 전체 흐름 (Zero → Live)

A/B도 모든 Target 활동 공통의 **3단계 가이드 워크플로우**.

```text
   ┌──────────────────────────────┐
   │ ① Experiences(변형 만들기)   │  위치(mbox) + 변형 A/B…N 콘텐츠
   └──────────────┬───────────────┘
   ┌──────────────▼───────────────┐
   │ ② Targeting(대상·트래픽)     │  오디언스 + 트래픽 분배 방식·비율
   └──────────────┬───────────────┘
   ┌──────────────▼───────────────┐
   │ ③ Goals & Settings           │  목표 지표·리포팅 소스·기간
   └──────────────┬───────────────┘
                  ▼
            Activate(게시) → 진입자에게 랜덤 분배·측정
```

| 단계 | 할 일 | Target UI |
|------|-------|-----------|
| 1 | 위치(mbox)·변형 콘텐츠 | Create Activity > A/B Test |
| 2 | 오디언스 + **Traffic Allocation** 선택 | (같은 마법사) Targeting |
| 3 | 목표 지표·리포팅·일정 | Goals & Settings |

---

## 1. 핵심 개념 (용어 7개)

| 용어 | 한 줄 |
|------|-------|
| **Experience(변형)** | 비교할 콘텐츠 1개(A, B, C…). 보통 A=기본(대조군) |
| **Control(대조군)** | 비교 기준이 되는 기본 변형(보통 A) |
| **Traffic Allocation** | 진입자를 변형에 나누는 방식·비율(예: 50/50) |
| **Goal Metric(목표 지표)** | 성과 측정 기준(전환·매출 등) |
| **Lift(향상도)** | 대조군 대비 성과 차이 |
| **Confidence(신뢰도)** | 결과가 우연이 아닐 확률(95%+ 권장) |
| **Sample Size(표본 크기)** | 유의미 판정에 필요한 방문자 수 |

## 2. A/B 활동 3종 (트래픽 분배 방식)

| 종류 | 동작 | 언제 |
|------|------|------|
| **Manual(수동·기본)** | 내가 정한 **고정 비율**로 랜덤 분배(예: 50/50). 승자는 내가 판정 | 정직한 비교 실험 |
| **Auto-Allocate(자동 분배)** | 성과 좋은 변형에 **트래픽 자동 증대**(탐색용 트래픽은 유지). 신뢰구간 안 겹치면 **승자 자동 선언** | 빨리 전환 올리며 승자 찾기 |
| **Auto-Target(자동 타게팅)** | ML이 **방문자 프로필별로 가장 맞는 변형**을 개인화 전달 | 세그먼트별 최적화(개인화) |

> 선택은 ② Targeting의 **Traffic Allocation** 컨트롤에서 전환. (Manual / Auto-Allocate to best experience / Auto-Target for personalized experiences)
> - **Auto-Allocate:** "control" 개념 없음. 모든 쌍 비교로 **진짜 승자** 판정. 권장 최소 **1,000 방문자 + 50 전환**.
> - **Manual:** 고정 기간(fixed horizon) 실험 → **표본 크기 계산기**로 기간 산정(§4).

---

## 3. 만드는 순서 (Create)

> 웹은 **VEC(시각 편집)**, **DOM 없는 네이티브/서버사이드는 Form-Based**(§6).

1. `Activities > Create Activity > A/B Test`.
2. **Visual(VEC)** 또는 **Form** 선택. (Premium은 **Workspace** 선택 가능)
3. **Activity URL**(VEC) 또는 **Location=mbox**(Form) → Create.
4. **활동 이름** 지정.
5. **변형 만들기** — A(기본)에서 **Add Experience**로 B, C… 추가, 각 변형 콘텐츠 편집.
6. **Targeting** — 오디언스 선택 + **Traffic Allocation**(방식·비율) 지정(§2).
7. **Goals & Settings** 지정(§5).
8. 우측 상단 **Activate**(게시).

## 4. 트래픽 분배 · 통계 (가장 헷갈리는 부분)

### 4.1 랜덤 분배의 진실

```text
진입자 도착 → 난수 생성 → 목표 비율(예: 50/50)에 따라 변형 선택
   초기엔 트래픽 적어 비율이 한쪽으로 쏠릴 수 있음
   → 트래픽 늘수록 목표 비율에 수렴
```

- 비율은 "목표값". **트래픽이 적으면 실제 분배가 안 맞아 보일 수 있음**(정상). 많아지면 맞춰짐.
- **한 번 변형에 배정된 방문자는 전환까지 그 변형 유지**(A/B·MVT 특성). → 그래서 다시 봐도 같은 게 나옴(§8 디버깅 참고).

### 4.2 얼마나 오래 돌리나 (표본 크기)

| 방식 | 기간 판단 |
|------|-----------|
| **Manual** | **Sample Size Calculator**로 사전 산정(고정 기간). 너무 일찍 끝내면 거짓 양성 |
| **Auto-Allocate** | 신뢰구간 안 겹치면 **자동 승자 선언**(계산기는 대략 참고용) |

- 권장: **신뢰도 95% 이상 + 통계적 검정력(power) 80%**.
- Auto-Allocate는 반복 평가에 따른 거짓 양성을 **Bernstein 부등식 기반 신뢰구간**으로 보정 → 멈출 때 "승자가 진짜 최적 대비 1% 이내일 확률 95%+".

## 5. Goals & Settings (목표·설정)

| 항목 | 내용 |
|------|------|
| **Reporting Source** | **Target** 또는 **Analytics(A4T)**. (Analytics면 목표 지표는 Conversion만) |
| **Goal Metric** | 성공으로 칠 행동(전환·매출·참여 등) + 세부 파라미터 |
| **Priority** | Low/Med/High 또는 0~999. **같은 위치+오디언스 활동 겹칠 때** 결정(`01_XT.md §7`) |
| **Audiences for Reporting** | 리포트를 특정 오디언스로 필터(기본 전체) |
| **일정/노트** | 시작·종료, 메모 |

> 목표 달성 후에도 방문자는 더 높은 우선순위 활동에 들지 않는 한 같은 변형 유지. 재달성 시 전환 추가 카운트.

## 6. 네이티브(앱/서버사이드) A/B — VEC 없이

> 핵심: **네이티브 RN엔 DOM이 없어 VEC로 "요소 바꾸기"를 못 한다.** → **Form-Based**로 만들고, **변형마다 콘텐츠(JSON/문자열)** 를 주면 **앱 코드가 받아서 반영**.

```text
[A/B 활동(Form)]  Location = mbox, 변형 A/B 콘텐츠(JSON: 예 imageUrl) + 트래픽 50/50
        │
        ▼
[앱]  retrieveLocationContent(mbox)  →  랜덤 분배된 변형의 콘텐츠 수신
        │
        ▼
앱 코드가 값(imageUrl 등) 해석 → 화면 반영(없으면 기본/대조군)
```

- 예: 이미지 A/B면 활동이 변형별로 `{"imageUrl":"..."}`(A URL / B URL)를 내려주고, 앱은 그 URL을 `<Image source={{ uri }}>`로 표시.
- **VEC식 자동 요소 치환 불가** — Target은 값만, **적용 대상은 앱이 결정**.

## 7. 본 프로젝트 적용 (네이티브 A/B 이미지 화면)

| 구성 | 값 |
|------|----|
| 화면(라우트) | `app/abtest.tsx` → `AbTestScreen`(푸터 "A/B 테스트") |
| mbox | `target-global-msdk-mbox`(= `config.mobile_env.adobe_sdk_mboxes.global_sdk_mbox_name`, `common.GLOBAL_MBOX`) |
| 자동 호출 | **진입 시 1회** global mbox 호출(`useEffect`) → 오른쪽 이미지에 반영 |
| 오퍼 계약 | 전용 파서 없이 **`{"imageUrl":"..."}` 단일 계약**(`extractImageUrl`) |
| 레이아웃 | 좌=기본(`default.png`, 대조군 고정) / 우=오퍼 이미지(URL). 각 칸 폭에 맞춰 `resizeMode="contain"`(비율 유지 자동 축소) |
| 폴백 | 오퍼 없음/로드 실패(`onError`) → "(오퍼 없음)" 표시 |
| 방문자 | `VisitorPanel` — 식별자 표시 + 새로고침 + 경험 초기화 |
| 미설정 경고 | mbox 빈값/웹 환경이면 `SupportBanner` 경고(하드코딩 폴백 없음) |

**동작 흐름**

```text
[화면 진입]
   → retrieveTargetContent("target-global-msdk-mbox", "")
   → JSON에서 imageUrl 추출 → 오른쪽 이미지 적용
   → getTargetIds()로 방문자 식별자 갱신
[다시 불러오기 버튼] → 같은 호출 반복
[경험 초기화] → tntId+ECID 제거 → 다음 호출에서 새 방문자로 A/B 재추첨
```

> 구현 상세·SDK 동작 → `docs/main/04_AT_TEST_PAGE_ADOBE_TARGET_INTEGRATION.md §14~15`.

## 8. 가드레일 · 자주 막히는 점

| 증상 | 원인 / 조치 |
|------|-------------|
| 50/50인데 새로고침해도 **계속 같은 변형** | 정상 — 한 번 배정되면 방문자가 그 변형에 **고정**됨. 다른 변형 보려면 **경험 초기화(tntId+ECID 제거)** 후 재호출(§7) |
| 초기 분배가 비율과 안 맞음 | 트래픽 적을 때 쏠림(정상). 트래픽 늘면 수렴(§4.1) |
| 오른쪽 이미지가 "(오퍼 없음)" | 활동 미게시 / mbox 불일치 / 오퍼 JSON에 `imageUrl` 없음 / 이미지 URL 로드 실패 |
| 결과 신뢰 어려움 | 표본 부족 → 신뢰도 95%·power 80% 충족까지 더 돌리기(또는 Auto-Allocate)(§4.2) |
| 여러 활동이 겹쳐 엉뚱한 게 보임 | 같은 위치+오디언스 → **우선순위(0~999)** 조정(`01_XT.md §7`) |
| 웹에서 SDK 동작 안 함 | 네이티브 빌드에서 테스트(웹은 프록시 경로) — `SupportBanner` 경고 확인 |
